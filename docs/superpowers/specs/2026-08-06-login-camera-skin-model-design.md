# 로그인·카메라·피부 분석 모델 통합 설계

- 상태: 사용자 승인 완료
- 작성일: 2026-08-06
- 대상 프로젝트: Dynamic Beauty Curator

## 1. 목적

현재 프로토타입의 고정 사용자 이름, 가짜 카메라 화면, 타이머 기반 가짜 피부 분석을 실제 사용자 흐름으로 교체한다.

완성된 흐름은 다음과 같다.

1. 사용자가 닉네임을 입력해 로컬 프로필을 만든다.
2. 브라우저 카메라 또는 사진 파일에서 얼굴 이미지를 가져온다.
3. 백엔드가 전달받은 Keras 모델로 색소침착·건조·모공·주름·민감 위험도를 추론한다.
4. 추론 결과와 위치 기반 환경 데이터, 기존 분석 룰북을 결합한다.
5. 위험도에 따라 추천 문구와 제품 순서를 변경한다.
6. 사진은 추론 중 메모리에서만 사용하고 저장하지 않는다.

## 2. 확정된 모델 사양

모델의 유일한 기준은 `backend_package.zip`에 포함된 실제 산출물이다. 이전에 전달된 224×224, 메타데이터 입력, 4개 출력 모델 설명은 사용하지 않는다.

- 모델 파일: `final_model.keras`
- SHA-256: `E835BB5686FF5C3DDF83BA92D52EB7CB4D2E100D1097178775B08A68F313EB15`
- 모델명: `efficientnetb2_skin_multitask`
- 모델 파일 크기: 65,653,012 bytes
- 입력 이름: `image`
- 입력 shape: `(None, 260, 260, 3)`
- 입력 색상: RGB
- 입력 dtype: `float32`
- 외부 픽셀 범위: `0~255`
- 외부 정규화: 없음
- 내부 전처리: EfficientNetB2의 `Rescaling(1/255)` 포함
- 출력 이름: `risk_probabilities`
- 출력 shape: `(None, 5)`
- 출력 activation: sigmoid
- 출력 순서: `pigmentation`, `dryness`, `pore`, `wrinkle`, `sensitivity`
- 위험 점수: `round(probability * 100)`
- 패키지 지정 실행 버전: TensorFlow 2.17.1
- 모델 저장 메타데이터: Keras 3.14.1

외부에서 `/255`, `preprocess_input`, `Rescaling`을 추가하면 이중 정규화가 되므로 금지한다.

모델 패키지는 구현 시 `backend/model/skin_multitask/`에 배치한다. 설정 JSON과 체크섬 문서는 저장소에서 관리하되, 65MB `.keras` 파일과 얼굴 샘플 이미지는 일반 Git에 커밋하지 않는다. 실행 환경에는 별도 모델 배치 단계로 제공한다.

## 4. 사용자 흐름

### 4.1 첫 방문

1. 앱은 `dbc.nickname` 로컬 저장값을 확인한다.
2. 저장값이 없으면 로그인 화면을 표시한다.
3. 사용자가 닉네임을 입력하고 계속하기를 누른다.
4. 닉네임을 저장하고 기존 온보딩으로 이동한다.
5. 위치·카메라 안내와 피부 타입 설정을 마치면 홈으로 이동한다.

### 4.2 재방문

저장된 닉네임이 있으면 홈으로 바로 이동한다. 현재 범위에서는 피부 타입을 서버 계정에 저장하지 않으며 기존 앱 기본값을 유지한다.

### 4.3 분석

1. 사용자가 홈에서 오늘의 분석 버튼을 누른다.
2. 카메라 화면이 실제 사용자 카메라를 요청한다.
3. 사용자가 촬영하거나 사진 파일을 선택한다.
4. 프론트는 사진, 닉네임, 위도, 경도, 피부 타입을 `/analyze`로 전송한다.
5. 분석 화면은 실제 요청 상태를 표시한다. 고정 3.6초 타이머로 성공 처리하지 않는다.
6. 성공하면 분석 결과와 추천 응답을 앱 상태에 저장하고 결과 화면으로 이동한다.
7. 실패하면 가짜 결과 대신 오류 원인, 재시도, 재촬영 동작을 표시한다.

### 4.4 로그아웃

마이페이지에서 로그아웃을 누르면 `dbc.nickname`을 삭제하고 사용자 상태를 초기화한 뒤 로그인 화면으로 이동한다.

## 5. 프론트엔드 설계

### 5.1 사용자 상태

`App.jsx`의 컨텍스트에 다음 상태를 추가한다.

```js
user: {
  nickname: string
}
```

닉네임 규칙은 다음과 같다.

- 앞뒤 공백 제거
- 길이 1~12자
- 빈 문자열 거부
- 브라우저 `localStorage` 키는 `dbc.nickname`
- 실제 인증 계정이 아니라 기기에 저장되는 로컬 프로필임을 로그인 화면에 명시

화면 변경:

- 화면 레지스트리의 첫 화면으로 `login` 추가
- 최초 로그인 후 `onboarding` 이동
- 저장된 닉네임이 있으면 초기 경로를 `home`으로 설정
- 홈의 `세현님`을 `${nickname}님`으로 변경
- 마이페이지의 `김세현`을 닉네임으로 변경
- 프로필 원형 문자는 닉네임의 첫 글자를 사용
- 실제 계정으로 오인될 수 있는 고정 이메일은 `이 기기에 저장된 로컬 프로필` 문구로 교체
- 로그아웃 버튼에 실제 동작 연결

### 5.2 카메라

카메라 화면은 다음 자원을 가진다.

- `<video playsInline muted autoPlay>` 미리보기
- `MediaStream` 참조
- 캡처용 `<canvas>` 또는 비표시 canvas ref
- 파일 선택용 `<input type="file" accept="image/jpeg,image/png,image/webp" capture="user">`

카메라 요청:

```js
navigator.mediaDevices.getUserMedia({
  video: { facingMode: 'user' },
  audio: false,
})
```

온보딩의 카메라 `허용하기` 버튼도 같은 API를 호출해 실제 권한을 요청한다. 권한 확인용 stream은 성공 직후 모든 track을 정지한다. 온보딩에서 건너뛴 경우 카메라 화면 진입 시 다시 요청한다.

미리보기만 좌우 반전한다. 모델에 전달하는 픽셀은 원본 방향으로 캡처한다. 화면 이탈·재촬영·컴포넌트 해제 시 모든 `MediaStreamTrack`에 `stop()`을 호출한다.

촬영 결과는 JPEG Blob으로 만들고 즉시 분석 요청에 사용한다. 파일 선택 이미지는 백엔드에서 EXIF 방향을 보정한다.

### 5.3 분석 API 클라이언트

`frontend/src/api/client.js`에 `analyzeSkin`을 추가한다. 요청은 `FormData`이며 `Content-Type` 헤더는 브라우저가 boundary와 함께 설정하도록 직접 지정하지 않는다.

전송 필드:

- `image`: 이미지 Blob 또는 File
- `nickname`: 닉네임
- `lat`: 위도
- `lng`: 경도
- `skin_type`: 사용자가 설정한 피부 타입

요청에는 60초 timeout과 `AbortController` 취소를 적용한다.

### 5.4 분석 진행 화면

기존 타이머 기반 완료 로직을 제거한다. 진행 화면은 다음 실제 상태를 사용한다.

- `preparing`: 이미지 준비
- `uploading`: 서버 요청 진행
- `completed`: 응답 검증 완료
- `error`: 실패

HTTP 한 요청 내부의 모델 추론과 추천 단계를 임의로 완료 처리하지 않는다. 기다리는 동안 단계 문구는 안내용 애니메이션으로 표시하되 결과 화면 이동은 성공 응답 이후에만 수행한다.

### 5.5 결과 화면

모델이 출력하지 않은 기존 가짜 종합 피부 점수는 제거한다.

- 상단 원형 표시: 가장 높은 위험 항목과 `risk_score`
- 집중 케어 태그: 확률 기준 상위 2개 항목
- 피부 지표: 5개 모델 출력 전체
- 각 지표: 한국어 이름, 확률 기반 0~100 점수, threshold badge
- threshold 이상: `우선 관리`
- threshold 미만: `낮음`
- 분석 시각 표시
- `의료 진단이 아닌 화장품 추천용 AI 분석입니다.` 안내

threshold는 결과 badge에만 사용한다. 추천 순서는 threshold 이진 판정 대신 연속 확률 전체를 사용한다. 이는 threshold 0.20에서 여러 target의 false positive가 많은 모델 특성을 완화하기 위함이다.

결과 경로에 분석 데이터가 없으면 고정 mock을 표시하지 않고 카메라 화면으로 안내한다.

## 6. 백엔드 설계

### 6.1 의존성

기존 FastAPI 의존성에 다음을 추가한다.

- TensorFlow 2.17.1을 1차 호환 기준으로 사용
- NumPy
- Pillow
- python-multipart
- 테스트용 pytest와 HTTP 클라이언트

모델이 Keras 3.14.1로 저장됐으므로 실제 샘플 로딩 테스트를 의존성 확정의 기준으로 삼는다. TensorFlow 2.17.1에서 로드할 수 없으면 모델·입력·출력 사양은 변경하지 않고, 해당 모델을 정상 로드하는 호환 TensorFlow/Keras 조합만 조정한다.

### 6.2 모델 서비스

새 `skin_analyzer` 모듈이 다음 책임을 가진다.

- `inference_config.json` 로드
- 파일 체크섬 및 필수 설정 검증
- `keras.models.load_model(..., compile=False)`로 모델 1회 로드
- 이미지 바이트 디코딩
- EXIF 방향 보정
- RGB 변환
- 260×260 resize
- `float32`, 0~255 유지
- batch 차원 추가
- 모델 추론
- 5개 출력 shape·순서·유한값·0~1 범위 검증
- 확률, 위험 점수, threshold badge 생성
- 가장 높은 위험과 상위 2개 위험 선택

모델은 애플리케이션 시작 시 로드를 시도한다. 실패해도 서버 헬스 체크는 가능하게 두되 모델 상태를 `unavailable`로 기록하고 `/analyze`는 503을 반환한다. 추론은 이벤트 루프를 막지 않도록 worker thread에서 실행하며, 단일 프로세스 내 모델 인스턴스를 공유한다.

### 6.3 이미지 검증과 보관 정책

- 허용 MIME: `image/jpeg`, `image/png`, `image/webp`
- 최대 전송 크기: 10MB
- 빈 파일 거부
- 디코딩 불가능한 파일 거부
- 과도한 해상도의 decompression bomb 거부
- 파일명·사진 바이트·사진 hash를 로그에 남기지 않음
- 파일 시스템에 저장하지 않음
- 응답 후 이미지 참조 해제

### 6.4 API

`POST /analyze` multipart endpoint를 추가한다.

응답 개념 구조:

```json
{
  "analyzed_at": "ISO-8601 timestamp",
  "model": {
    "name": "efficientnetb2_skin_multitask",
    "version": "package checksum prefix"
  },
  "skin_analysis": {
    "pigmentation": {
      "label_ko": "색소침착",
      "probability": 0.42,
      "risk_score": 42,
      "threshold": 0.2,
      "risk_label": "high"
    }
  },
  "focus_risks": ["dryness", "sensitivity"],
  "main_risk": "dryness",
  "main_risk_score": 74,
  "message": "닉네임과 피부·환경을 반영한 문구",
  "env_data": {},
  "recommendations": [],
  "avoid": [],
  "ranking_signals": [],
  "rule_id": "기존 환경 룰 ID",
  "is_fallback": false
}
```

기존 `POST /recommend`는 홈의 환경 기반 기본 추천을 위해 유지한다. `/analyze`는 모델 결과가 포함된 정밀 추천을 반환한다. 두 endpoint는 같은 환경 조회와 룰북 함수를 공유한다.

오류 상태:

- 400: 빈 파일 또는 디코딩 불가
- 413: 10MB 초과
- 415: 지원하지 않는 이미지 형식
- 422: 폼 필드 검증 실패
- 503: 모델 미배치 또는 로딩 실패
- 500: 내부 추론 실패. 사용자 응답에는 민감한 내부 예외를 노출하지 않음

## 7. 위험도 기반 추천 설계

### 7.1 위험 규칙

새 `backend/data/skin_risk_rules.json`에서 모델 target과 제품 카테고리·성분·회피 성분을 매핑한다.

- `pigmentation`: 선케어, 나이아신아마이드, 비타민C
- `dryness`: 보습 토너·크림, 히알루론산, 세라마이드, 판테놀
- `pore`: 클렌징, BHA, 나이아신아마이드
- `wrinkle`: 앰플·장벽 크림, 펩타이드, 아데노신
- `sensitivity`: 진정·저자극, 센텔라, 판테놀, 무향

조건부 회피 규칙:

- 민감 확률이 높으면 향료·에센셜오일·고농도 산 성분 감점
- 자외선 등급이 높음 이상이면 고농도 AHA와 레티놀 감점
- 미세먼지 등급이 나쁨 이상이면 클렌징·진정 신호 가산
- 자외선 등급이 높음 이상이면 선케어·색소 관리 신호 가산

### 7.2 추천 합성

기존 `rules.json`의 피부 타입·미세먼지·자외선 규칙을 기본 추천으로 유지한다. 모델 위험 규칙은 확률이 높은 순서로 합치고 동일 카테고리·성분은 중복 제거한다.

추천 문구는 다음 순서로 만든다.

1. 닉네임
2. 가장 높은 피부 위험 2개
3. 현재 환경의 주의 조건
4. 우선 추천 카테고리 또는 성분 2개

예시:

> 민지님은 오늘 건조와 민감 신호가 높고 자외선도 강해요. 판테놀 진정 제품과 자외선 차단제를 먼저 추천해요.

### 7.3 제품 정렬

프론트의 기존 제품 카탈로그를 유지하고 백엔드가 반환한 `ranking_signals`를 사용한다.

개념 점수:

```text
final_score = existing_match
            + sum(risk_probability × category_match_weight)
            + sum(risk_probability × ingredient_match_weight)
            + environment_rule_bonus
            - avoid_penalty
```

가중치:

- 위험 순위 배수: 1위 `1.0`, 2위 `0.75`, 나머지 `0.35`
- target별 카테고리 일치: `18 × probability × 위험 순위 배수`
- target별 성분 일치: `12 × probability × 위험 순위 배수`; target 하나당 최대 24점
- 기존 환경 룰 카테고리·성분 일치: 건당 10점, 최대 20점
- 회피 성분 일치: 건당 100점 감점
- 성분 비교: 공백과 대소문자를 정규화한 뒤 양방향 부분 일치

추가 규칙:

- 모든 계산은 결정론적으로 수행
- 상위 위험 2개가 가장 큰 가중치를 갖지만 나머지 3개 확률도 반영
- 회피 성분이 매칭되면 다른 가산점보다 큰 감점 적용
- 정렬 동점은 기존 `match`, 평점, 원래 순서로 안정적으로 해소
- 제품 카드의 추천 이유에는 실제로 적용된 가장 큰 신호를 표시

## 8. 개인정보 및 사용자 안내

- 앱은 촬영 전에 사진이 백엔드로 전송되어 메모리에서 분석된다는 사실을 안내한다.
- 기존의 `이미지는 기기에서만 처리` 문구를 제거한다.
- `분석 후 즉시 폐기`, `서버 파일로 저장하지 않음`을 정확히 표시한다.
- 얼굴 분석 결과는 의료 진단이 아니며 화장품 추천 보조 정보임을 명시한다.
- 닉네임과 사진은 서버에 영구 저장하지 않는다.
- 로그에는 닉네임 전체와 이미지 관련 식별값을 기록하지 않는다.

## 9. 오류 처리

### 프론트엔드

- 카메라 API 미지원: 파일 선택 안내
- 권한 거부: 브라우저 설정 안내, 재시도, 파일 선택
- 카메라 장치 없음: 파일 선택
- 장치 사용 중: 재시도 안내
- 촬영 실패: 카메라 유지 후 재촬영
- 업로드 timeout: 재시도 또는 재촬영
- 모델 503: 모델 준비 오류 안내
- 잘못된 이미지: 다른 사진 선택 안내
- 요청 취소: 오류 결과를 남기지 않고 홈 또는 카메라 복귀

### 백엔드

- 시작 시 모델 상태 기록
- 예측 결과 shape 불일치 시 요청 실패
- NaN·Infinity·범위 이탈 출력 거부
- 예외 세부 내용은 서버 로그에만 남기고 사용자에게는 안전한 메시지 반환
- 환경 API 실패는 기존 fallback을 사용하되 `is_fallback`으로 표시
- 환경 fallback과 모델 실패는 서로 다른 상태로 처리

## 10. 테스트 설계

### 10.1 모델 계약 테스트

- ZIP의 `sample_01.jpg`, `sample_02.jpg`를 로컬 전용 fixture로 사용
- `expected_predictions.json`과 target별 확률 절대 오차 `1e-4` 이내
- 위험 점수 오차 0~1점
- 입력 크기 260×260×3 확인
- RGB 확인
- 외부 `/255`가 적용되지 않았음을 회귀 테스트
- 출력 순서와 5차원 shape 확인
- 모델 체크섬 확인

얼굴 샘플 이미지는 Git에 커밋하지 않는다.

### 10.2 백엔드 단위·API 테스트

- 지원 이미지 정상 분석
- MIME·용량·빈 파일·손상 파일 거부
- 모델 미배치 시 503
- 모델 출력 파싱과 focus risk 순서
- 다른 위험 벡터에서 추천 문구와 ranking signal이 변경됨
- 민감·고자외선 조건에서 회피 규칙 적용
- 닉네임을 포함한 메시지 생성
- 환경 fallback 상태 보존

### 10.3 프론트엔드 테스트

- 닉네임 입력 검증
- localStorage 저장과 재방문
- 홈·마이페이지 이름과 프로필 글자 반영
- 로그아웃 시 저장값 삭제와 로그인 이동
- 카메라 성공·거부·미지원 상태
- unmount 시 track 정지
- 촬영 Blob과 FormData 필드
- 분석 성공 시 mock이 아닌 API 결과 표시
- 분석 실패 시 재시도 동작
- 5개 위험 카드와 상위 2개 태그
- 위험 신호 변화에 따른 제품 정렬 변화

### 10.4 전체 흐름 검증

1. 백엔드 모델 샘플 계약 테스트
2. 백엔드 전체 테스트
3. 프론트 단위 테스트와 lint
4. 프론트 production build
5. 브라우저 자동화에서 로그인 → 권한 → 촬영 또는 fixture 업로드 → 분석 → 결과 → 추천 → 로그아웃
6. 실제 Windows 브라우저에서 카메라 권한 허용·거부 수동 점검

## 11. 완료 기준

- 고정 이름 `세현`, `김세현`이 사용자 노출 경로에서 제거된다.
- 입력한 닉네임이 홈과 마이페이지에 반영되고 재방문 시 유지된다.
- 카메라 화면이 실제 video stream을 표시한다.
- 촬영 또는 파일 선택 이미지가 `/analyze`로 전송된다.
- ZIP 모델의 두 샘플 출력이 예상값과 허용 오차 내에서 일치한다.
- 결과 화면이 API의 5개 확률을 사용하며 고정 `SKIN_ANALYSIS`를 사용하지 않는다.
- 위험 벡터가 달라지면 추천 문구와 제품 순서가 달라진다.
- 이미지가 파일 시스템에 저장되지 않는다.
- 카메라·모델·이미지 오류에서 가짜 성공 화면으로 이동하지 않는다.
- 테스트, lint, production build, 전체 브라우저 흐름 검증이 통과한다.
